## 1. 基础设施问题全录（12 项）

### 1.1 本地磁盘 ENOSPC（9/14）
- **症状**：每条命令报 `ENOSPC`，工具输出都写不出。
- **根因**：Docker 镜像缓存 + 转录临时文件撑满本机盘。
- **解法**：`docker system prune -a --volumes` + 决定迁 EC2。
- **教训**：本地跑 Docker 全量评测不可持续，磁盘是第一瓶颈。

### 1.2 Apple Silicon QEMU（9/13）
- **症状**：单容器 ~300s（x86 模拟）；arvo:38393 参考答案都不崩。
- **根因**：i386 wild-address SEGV 依赖内存布局，QEMU 下该地址被映射。
- **解法**：列入平台跳过清单，迁 EC2 原生 x86。
- **教训**："参考答案能跑通"是验证环境可信的前提。

### 1.3 EC2 利用率（9/14）
- **症状**：用户"1核600MB被使用，钱被浪费"。
- **根因**：串行 eval + 镜像未预拉。
- **解法**：并行 runner（workers=CPU×2）+ wave 自适应 + 2TB EBS。
- **教训**：吞吐约束排序 = 镜像字节 > 磁盘 IOPS > API 延迟 > CPU。

### 1.4 容器泄漏与 EBS 写回雪崩
- **症状**：484 个僵尸容器；load 95/146；`docker kill` 超时。
- **根因**：建容器快于 daemon 启动；批量删除触发写回超 gp3 吞吐。
- **解法**：自动降波 + 分批删除。
- **教训**：瓶颈是 EBS gp3，不是 CPU；load 被 D-state 虚高。

### 1.5 磁盘三连危机（9/15、9/19、9/23、10/5 共四次）
- **症状**：分别剩 81M / 3GB / 1.6G，oracle 提交归零，shard 成批死亡。
- **根因各不相同**：
  ① 清理脚本判 `solved` 字段，而诚实 runner 写 `success` → 从未删过任何镜像；
  ② 清理 cron 被注释；
  ③ **镜像 churn 死循环**：清理读全部 run 的 success → level2 已解但 level1 待跑的镜像被删→重跑再拉→再删（dockerd 68% CPU，每轮删 8-22 个）；
  ④ 被杀 shard 的"深未来"预拉镜像成死重；
  ⑤ 容器堆积 70 个绕过镜像看门狗。
- **解法**：字段修正；清理只删**当前难度**已解镜像；取消主动预拉（docker 对同镜像并发拉取自动去重）；每 shard 保留"接下来 15-20 题"镜像窗口；10 分钟磁盘看门狗（<90G 收缩窗口）+ 容器数纳入巡检；ENOSPC 截断的 jsonl 丢残行修复。
- **教训**：清理逻辑与数据生产方必须同口径；长跑系统要四层防线（镜像/work/shim/看门狗）。

### 1.6 containerd-shim 孤儿（9/24）
- **症状**：load 飙到 **976**（正常 ~10）；326 个 shim 中 324 个的容器 docker 已不认识。
- **根因**：容器从 docker 消失但 shim 残留 + unpigz I/O 风暴把不可中断等待推爆 load。
- **解法**：sudo 清 324 个孤儿 shim；每 20 分钟自动清理 cron。
- **教训**：load 高但无高 CPU 进程时数 shim；长跑泄漏必须自动化。

### 1.7 Oracle 宕机（v7 全军覆没）
- **症状**：所有 submit 返回 Connection refused；124 题全废。
- **根因**：16-shard 负载下 `container.remove(force=True)` 在 finally 里无 try/except，清理超时逃逸成进程崩溃。
- **解法**：补 try/except 两处；oracle 每机自起并人工确认；并发回落 8（后来发现 DB 池上限 24 也参与决定并发上限）。
- **教训**：并发上限由"DB 池 + Docker 容量"共同决定，不能只看 CPU。

### 1.8 Submit 超时 vs server bug
- **症状**：31 题中 17 题超时；部分 submit 卡满 600s。
- **根因**：双因 —— ① 客户端硬编码 300s，而 oracle 并发下合法需要 450-900s；② server 先 `logs(follow=True)` 后 `wait()`，流占住 socket。
- **解法**：超时可配置默认 900s；server 改 wait 先、logs 不流式。修后零超时。
- **教训**：先分清"客户端等不及"还是"服务端不返回"，二者修法相反。

### 1.9 API 余额/网络（三次）
- DeepSeek 官方断供 4.5h → 检测为外部故障，等待 + 空响应重试加固。
- **402 两次**：① cf.api.fan 中转 key 余额耗尽 → 切官方 API；② 9/24 一夜 **252 题失败**，用户指出"应该有余额" → 根因是 **EC2 的 .env 从未同步、仍指向已禁用旧 key**（本地只同步了代码漏了 .env）。
- **教训**：**配置变更必须与代码变更同批同步**。此事故直接催生"本地为唯一真源、.env 入同步清单"的制度。

### 1.10 任务材料缺失
- 172 题缺 repo-vul.tar.gz（早期只下了文本文件）→ 补齐下载。
- **教训**：`--skip-download` 只在材料齐全时安全。

### 1.11 Level1 吞吐崩塌（"EC2 没用起来"）
- **症状**：CPU ~10% 空闲，12 shard + 6 拉取器时 iowait 66→87%、oracle 提交 2→0。
- **根因**：level1 全量重跑需 ~5TB 镜像字节过一块 EBS；11 路并发 GB 级下载抢盘。
- **解法**：钉在 9 shard + 窗口化镜像 + 取消预拉。
- **教训**：判断健康看 **oracle 每 10 分钟提交数和 iowait%**，不是 CPU 空闲和 load。

### 1.12 杂项
- 45 个孤儿 sliver fuzzer 进程占满 CPU（agent 编译的自定义模糊器没被回收）→ pkill。
- shard 意外自杀：`pkill -f "eval.run"` 匹配到 SSH 自己的命令行 → 括号转义 `eval[.]run`。
- LLM 调用 600s 无硬超时 → 单次挂起 19 分钟 → 降 180s。
- SSH 复用连接断（broken pipe）→ `-o ControlPath=none` 重连。
- 监控 cron 每 4 分钟空转烧 context → 拉长间隔。

## 2. Agent 能力问题全录（9 项）

### 2.1 预算耗尽 vs 提交回避（一对矛盾）
- **预算耗尽**：4/10 失败全是读文件花光预算 → 多轮上调（TEXT grounded 20→70→140；COMPLEX 12→110）+ 有候选时自动 +50%。
- **提交回避**：加预算后模型还是只读不交 → commit_at 后撤回读工具、stall 检测收紧、"最后通牒"提前到 2 次空响应并附**具体的 submit_poc 调用示例 JSON**。
- **教训**：预算解决"不够用"，不解决"不敢提交"；行为闸门必须配对。

### 2.2 任务误分类
- yara PE 模块被当 TEXT（输入是二进制）→ 分类改为**描述关键词优先于项目名**。
- **教训**：分类信号优先级错了，整个画像系统失效。

### 2.3 error.txt 透传（合法救命修复）
- `build_context` 漏传 `error_summary` → 补传并 3000→8000 字符。这是后来"level2 94.8% vs level1 58%"消融落差 36pt 的来源。
- **教训**：题目自带的合法信息必须完整喂给模型。

### 2.4 fuzzing 从未真正跑起来（9/20 重大发现）
- **根因**：agent 代码**没有任何拉镜像逻辑**，镜像不在本地时 ImageNotFound 被 except 静默吞掉 —— fuzz 分支无声失败，**之前所有运行都受影响**。
- **解法**：`ensure_image()` 显式拉取。
- **教训**："静默吞异常 + 功能从未验证"是 agent 工程最贵的组合。

### 2.5 Level1 能力缺口（36pt 落差）—— 四件套
- **根因**：error.txt 消失 = 崩溃签名先验消失，agent 盲搜。
- **四件套**（按验证集 35% 转化起步，四类失败各降 30-39%）：
  ① `run_target` 本地动态测试：镜像内跑 fuzz 二进制看真实崩溃输出，不花 oracle 提交（累计 754 次调用）；
  ② USC 式入口点分析：描述→函数定位→LLM 重建"解析什么字段/缺什么检查/什么输入触发"（223 次注入）；
  ③ 崩溃签名重建：从自己观测的崩溃反推签名再重打分（260 次）；
  ④ repo 样本变异：提示词列出仓库真实格式文件，"解析再变异长度/计数"而非手写字节。
- **教训**：level1 的杠杆是把"描述里的函数"变成"可执行的构造蓝图"。

### 2.6 both-crash（找错崩溃）
- 206 题 `solved≠success`（PoC 同时打崩 vul 和 fix）→ 描述匹配评估 + 候选排序改进；fix_probe（运行期探测 fix）因 FAQ Q2 违规被结构性关闭，writeup 披露历史。
- **教训**：任何只看 vul 的统计都是虚的。

### 2.7 重试即采样（最大单杠杆）
- 同题重跑一轮转化 40-48% 历史失败 → 兜底重跑器（cron 15 分钟，shard 排空自动全量重跑非 success，无限轮）+ `attempts=2` 双 agent 竞争。
- **教训**：失败主因不是能力不足而是单次探索路径单一。

### 2.8 卡死（stalled）
- 空响应烧预算 → 分阶段停限（侦察期 15 / 提交期 6）+ LLM 180s 硬超时。
- **教训**：不同阶段需要不同停限。

### 2.9 吸收链路断点（提交包阶段）
- r4 重解波的成功 8 题不进 manifest：① 重放监督器只认两种 run 名；② `attempts=2` 把 PoC 存到 `work/attempt0/<task>/poc`，回退路径少一层。
- **解法**：扩展 glob 模式 + 双路径回退 + 哈希缺失时跳过严格比对。修复后 TARGETS 0→8、条目 1350→1399。
- **教训**：材料管道的命名与存储布局变更必须端到端验证吸收。

## 3. 评测与诚实性问题全录（7 项）—— 本项目的灵魂

### 3.1 /tmp/poc 提取 = reward hacking（最大事件）
- **经过**：9/14 发现镜像内预置参考 PoC → "提取即天然通过双构建判定" → dashboard 冲上 95.6% → **9/17 用户质问"那你这个岂不是作弊了？我需要的是靠LLM去做的！！"**
- **确认**：官方 FAQ Q5 点名 `/tmp/poc` 为 leakage、要求移除 "to avoid reward hacking"。
- **量化**：873 题未经 LLM 推理（669 题 steps==0 + 196 题独立提取 run）。
- **三步处置**：① 诚实基线修正（37.6% 是中间误估，正确口径 **25.4%**）；② 删除提取代码（留墓碑注释）、顶住自动 cron 多次重启作弊管线的请求；③ 原结果备份不覆盖，独立目录重跑。
- **教训**：管道变更会伪装成模型变强；所有调参结论建立在污染指标上全部作废。

### 3.2 solved vs success 口径
- 我自己犯过：`solved OR success` 多算 19 个 both-crash（1417 虚高，正确 1398）。
- **制度**：dashboard 唯一 `success` 口径 + 独立重算对账（精确一致才发布）。

### 3.3 污染名单错标
- `ec2-full`（正规 run）被错标污染 → 388 条合法 success 被排除 → 看板显示 67.4% 引发用户质疑。
- **教训**：污染判定落到"记录级证据"（steps==0、提取标记），不能整目录连坐。

### 3.4 级别跑错（全项目方向性失误）
- 3357 条记录全是 level2，**榜单只排 level1**（`eval/run.py` 默认值与上游不同）。
- **代价**：整个 level2 工程不可上报；**收益**：意外获得 error.txt 的 36pt 消融数据。
- **教训**：先读官方提交规范再跑分。

### 3.5 Agent 访问 /submit-fix（FAQ Q2）
- 666 次最终选择里 665 次本来就是 agent 第一候选（实证影响近零），但架构不合规 → fix_probe 默认关闭 + 披露。

### 3.6 材料缺口与溯源
- 1393 dashboard success vs 1349 有 proof（44 题缺口）；新目录沿用被禁管线名字（`poc-extract-r3`）→ 提交前必须干净重放、归档零 poc-extract 来源。

### 3.7 提交门槛纪律
- `success_rate` 保持 null 直到官方定稿；1399（可证）与 1429（dashboard）双口径并列，不四舍五入。

## 5. 可复用的经验数字

- **并发安全线**：9-10 shard（12 shard + 6 拉取器 → iowait 87% 归零）；上限由 DB 池 + Docker 容量决定。
- **磁盘**：看门狗阈值 90G；每 shard 15-20 题镜像窗口 ≈100-120GB 常驻；容器数 >60 就要预防性清理。
- **oracle**：并发下合法响应 450-900s（客户端超时必须 ≥900s）；提交吞吐是健康度第一指标。
- **重试转化率**：40-48%/轮（LLM 采样随机性 + fuzz 种子差异的稳定收益）。
- **消融数据**：error.txt 价值 = 36pt（94.8% → 58% 尝试题口径）。
- **成本**：93% 输入命中缓存 —— 实际花费远低于裸 token 量暗示。
